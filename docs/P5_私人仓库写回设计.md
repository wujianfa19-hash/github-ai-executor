# P5 阶段C｜公开执行器 → 私人仓库 最小权限写回设计

> 用途：为 `github-ai-daily`（及两个雷达）迁移到公开执行器时，"公开仓库程序 → 私人仓库数据"的跨仓库写回方案。
> 状态：设计文档（已确认原则，待第二个任务迁移时落地验证）
> 创建：2026-09-21

## 一、要解决的问题

公开执行仓库 `wujianfa19-hash/github-ai-executor` 运行 GitHub Actions 时，其**自动生成的 `GITHUB_TOKEN` 只能写回自己这个公开仓库**，默认不能访问/写入私人仓库 `wujianfa19-hash/github-ai-daily-intelligence`。

但 `github-ai-daily` 的结果需要写回私人仓库（历史 JSON、reports）。

## 二、核心原则

1. **公开仓库 = 程序**：只负责临时计算，不永久保存私人数据。
2. **私人仓库 = 数据**：保存 state、reports、历史结果。
3. **最小权限**：只允许访问指定私人仓库 `github-ai-daily-intelligence`，只给任务真正需要的权限。
4. **明确禁止**：不给整个账号所有仓库权限、不给 administration、不给删除仓库、不给无关仓库。

## 三、两种可选方案

### 方案 A（推荐）：专用细粒度 Personal Access Token / App，限定单仓库 + 写入范围

- 在 GitHub 创建设置一个**只授权 `github-ai-daily-intelligence` 一个仓库**、权限仅 `Contents: Read/Write` 的凭据（细粒度 PAT 或 GitHub App）。
- 该凭据作为 Secret `PRIVATE_REPO_TOKEN` 存进公开仓库。
- 公开执行器工作流在"写回"步骤用 `PRIVATE_REPO_TOKEN` 而非默认的 `GITHUB_TOKEN`，向私人仓库 push。
- 优点：权限可精确到单仓库单目录；符合"最小权限"。
- 缺点：需要用户本人创建该凭据（我无法代替创建 OAuth App/PAT 授权）。

### 方案 B：先读私人 → 临时工作目录 → 本地运行 → 临时结果写回

- 公开执行器启动时用 `PRIVATE_REPO_TOKEN` 把私人仓库的 state/历史 clone 到临时工作目录。
- 程序在临时目录运行，产生临时结果。
- 验证后通过同一受限 token 只 push 结果相关文件。
- 与方案 A 本质相同，只是执行流程更细；二者可合并。

## 四、写回流程（目标形态）

```text
公开执行器启动
↓
受限 token 读取私人仓库 state / 历史输入
↓
复制到临时工作目录
↓
程序运行（调用模型）
↓
产生临时结果
↓
验证结果合法
↓
通过受限 token 写回私人仓库对应文件
↓
公开运行环境结束
↓
临时数据消失（不落在公开仓库）
```

## 五、执行顺序（第二个任务迁移时）

1. 先把 `github-ai-daily` 工作流做 dry_run 安全测试模式（默认不发正式邮件、不写正式历史，结果写 os.tmpdir）。
2. 确认程序链路（读数据、调模型、生成报告）真实可用。
3. 再建立受限凭据（PRIVATE_REPO_TOKEN，单仓库+contents write）。
4. 测试私人仓库读 → 临时计算 → 写回。
5. 最后才考虑真实正式切换（不提前）。
6. 正式切换 = 原私人定时停用 + 新公开定时启动，避免双运行。

## 六、验证标准

- 公开执行器能用受限凭据**只**写出/读入 `github-ai-daily-intelligence`。
- 公开仓库本身不出现私人结果文件。
- 日志不出现 PRIVATE_REPO_TOKEN 真实值。
- 陌生人 PR 无法获得受限凭据。
- 新旧定时不会同时正式运行。
